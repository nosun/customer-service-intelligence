## 适用范围

本文说明销售订单完成后，从创建物流运单到妥投、退回或作废期间的操作边界。它适用于正常发货、收件信息变更、渠道变更、承运商撤单、拦截退回、重新发货及常见物流异常。

本文不替代以下流程：

- 客户取消、退款和责任认定流程；
- 物流异常处理单的领取、跟进、理赔和结案流程；
- 承运商后台的具体操作手册；
- 生产重做和部分商品补寄的审批流程。

## 核心原则

1. 销售订单、客户确认地址和客户诉求以 `console-new` 为业务来源。
2. 运单状态、承运商物流单号、面单、取件时间和轨迹以 `tradeExpress` 为物流事实来源。
3. 承运商已经接收包裹后，必须保留原运单、物流单号、面单、轨迹和费用证据。
4. 已作废的运单不恢复、不重用；需要重新发货时创建新包裹和新运单。
5. “作废物流运单”不等于“取消销售订单”。客户取消必须从订单流程发起。
6. 客户退款、拒付或取消不等于物流投递失败；物流结果必须依据包裹实际去向确认。

## 操作前所需事实

执行任何修改、作废、重发或异常操作前，至少确认：

- 销售订单号和包裹号；
- `tradeExpress` 当前运单状态；
- 是否已经生成承运商物流单号或面单；
- 是否存在 `pickup_at` 或承运商取件轨迹；
- 仓库是否已经交接实物包裹；
- 客户最终确认的地址和诉求；
- 是否属于合并包裹、重发包裹或重做包裹。

仅凭客户描述、订单备注或单个页面显示，不足以覆盖物流事实。

## 生命周期与允许操作

| 阶段 | 系统现象 | 原包裹处理 | 允许的主要操作 |
| --- | --- | --- | --- |
| 尚未创建物流运单 | `console-new` 包裹为“未创建” | 可以继续使用 | 修正订单和包裹资料后创建运单 |
| 待处理 | `tradeExpress` 状态为“待处理”，尚未抛送承运商 | 可以继续使用 | 推送收件信息、修改渠道、核对后抛送；必要时本地作废后创建新包裹 |
| 抛送中 | `tradeExpress` 状态为“抛送中” | 暂停其他操作 | 等待本次抛送返回；超时须先核对承运商是否已经建单 |
| 已创建 | 承运商运单已生成，面单可能仍在下载 | 不直接修改 | 确认未取件后，按受控作废流程处理并创建新包裹 |
| 待取件 | 已有面单，承运商尚未取件 | 不直接修改 | 确认未取件后作废旧运单、销毁旧面单并创建新包裹 |
| 已取件或配送中 | 已有取件时间或取件轨迹 | 保留原运单 | 进入物流异常处理；联系承运商改址、拦截或退回 |
| 成功、失败、废弃、合并或客户取消 | 已进入终态 | 仅作历史保留 | 按对应售后、重发、理赔或订单流程处理 |

“抛送承运商”和“承运商已取件”是两个不同阶段。已生成物流单号或面单，并不代表承运商已经接收实物包裹。

## 标准发货流程

1. 在 `console-new` 核对客户、收件地址、电话、邮编、税号和特殊要求。
2. 核对应发商品、数量、申报信息、重量和物流渠道。
3. 在包裹管理中为“未创建”的包裹创建面单，将包裹资料发送到 `tradeExpress`。
4. 在 `tradeExpress` 确认运单处于“待处理”，并再次核对收件信息、商品、申报、重量和渠道。
5. 执行抛送，等待承运商返回物流单号和面单。
6. 核对面单地址、物流单号和实物包裹，确认一一对应后再交接仓库或承运商。
7. 取件后由系统同步状态和轨迹；异常统一进入物流异常处理流程。

## 资料变更处理

### 尚未向承运商抛送

适用条件：运单为“待处理”，不存在承运商物流单号和面单。

1. 暂停抛送和实物交接。
2. 先在 `console-new` 修改订单收件信息或其他业务资料。
3. 收件信息变更且“推送更新”可用时，从包裹管理将最新收件信息推送到 `tradeExpress`。
4. 物流渠道变更时，只能对“待处理”运单使用“修改渠道”。
5. 商品、申报或重量发生变更时，不得假定“推送更新”已经同步全部字段；不能确认一致时，应作废尚未抛送的旧运单，再以正确资料创建新包裹。
6. 返回 `tradeExpress` 逐项核对，确认信息正确后再抛送。

如果更新失败、功能不可用，或已经出现承运商结果，应停止继续修改并交由物流负责人处理。

### 已抛送但尚未取件

1. 通知仓库暂停交接，并将原包裹移出待交接区域。
2. 若状态仍为“抛送中”，先等待返回，不得并发发起作废。
3. 核对 `pickup_at`、承运商后台和轨迹，确认承运商确实尚未取件。
4. 在 `tradeExpress` 使用“作废运单”，填写真实原因和正确类型。
5. 作废失败时停止后续操作，保留原运单和旧面单。
6. 作废成功后，在 `console-new` 修改订单资料并使用“包裹重发”创建新包裹。
7. 创建新运单并核对新面单；销毁旧面单后才可恢复实物交接。

当前作废规则：

- 云途、燕文支持系统申请承运商撤单；
- 不支持自动撤单的渠道执行本地作废，但仍保留原物流证据；
- “历史合并发货补录”仅用于实际已经合并发货的历史记录纠正，不作为普通作废方式。

### 已取件或配送中

1. 不执行普通“作废并重新抛送”，不清空物流单号、面单、取件时间或轨迹。
2. 在 `console-new` 的“物流异常处理”中查找或跟进对应处理单。
3. 联系承运商申请改址、拦截或退回，并记录物流商工单号、申请时间和回复。
4. 改址成功时继续使用原运单跟踪。
5. 拦截退回时，等待承运商轨迹及实物去向确认，再决定重发、重做、退款或取消。
6. 无法拦截时继续跟踪签收、拒收或退回，不得伪造终态。

特殊边界：状态为“已取件”的运单，只有在已确认物流拦截退回后，才允许由物流负责人使用受控作废操作做本地失效记录。该操作不会调用承运商撤单，必须填写原因，并保留取件、物流单号、面单和轨迹证据。此例外不能扩展到仍在运输中的包裹。

## 退回后的处理

处理前必须确认物流轨迹和实物去向，并记录退回原因、责任方、承运商凭证及客户最终诉求。

- 商品可以直接再次寄出：使用“包裹重发”，创建新包裹和新运单。
- 商品需要重新生产：使用“订单重做”，完成生产和质检后再创建新包裹。
- 客户不再需要商品：不创建重发或重做包裹，转入取消、退款和责任认定流程。
- 只补寄原包裹中的部分现货商品：当前没有标准功能，暂停操作并由负责人确认，不能用整包“包裹重发”代替。

## 常见异常与处理入口

| 情况 | 正确入口 | 禁止行为 |
| --- | --- | --- |
| 创建运单失败 | 保存完整错误，修正资料后对原包裹重试 | 连续重复点击或重复创建包裹 |
| 抛送中超时 | 核对承运商未建单后使用受控恢复操作 | 未核对承运商就恢复或重试 |
| 云途提示重复订单 | 等待系统检查原单，必要时使用“检查运单” | 重复创建或手填旧物流单号 |
| 选错物流渠道 | 待处理时修改渠道；已抛送后作废并建新包裹 | 直接修改已抛送运单的渠道 |
| 订单完成后、取件前取消 | 从 `console-new` 的订单取消流程发起 | 只作废物流运单来代替取消订单 |
| 取件后客户取消 | 联系承运商拦截或退回，再处理订单和退款 | 绕过已取件限制直接取消或作废 |
| 承运商更换末端物流单号 | 使用“更换物流单号”并填写原因 | 直接编辑字段或删除原单号 |
| 长期无轨迹、丢件、破损、拒收或清关异常 | 使用物流异常处理单跟进 | 人工改成失败后停止跟踪 |
| 合并包裹需取消一个成员订单 | 由负责人核对全部成员和实物包裹 | 单独作废代表包裹或子包裹 |

## 操作记录要求

非正常操作至少记录：

1. 原订单号、包裹号和物流单号；
2. 当前运单状态、取件证据和实物去向；
3. 变更或异常原因；
4. 客户最终确认的诉求；
5. 责任方及认定依据；
6. 承运商工单号或其他凭证；
7. 作废、拦截、退回、重发、重做或退款的结果；
8. 新包裹号、新物流单号和面单核对结果。

## 禁止事项

- 禁止清空、删除或直接覆盖原物流单号、面单、取件时间和轨迹。
- 禁止恢复已作废运单或使用原包裹号重新抛送。
- 禁止在已抛送运单上直接修改收件信息、商品、申报价值或重量。
- 禁止把取件后的普通异常当作取件前作废处理。
- 禁止用物流作废代替销售订单取消。
- 禁止在撤单、拦截或退回结果未明确时重复创建新包裹。
- 禁止将超期信号直接解释为丢件、投递失败或责任结论。

## 升级规则

遇到以下情况必须暂停并升级给物流或订单负责人：

- 运单状态、`pickup_at`、承运商后台和轨迹互相矛盾；
- 作废或承运商撤单失败；
- 合并包裹只取消其中一个订单；
- 需要部分现货补寄；
- 无法确认包裹是否已被承运商接收；
- 客户取消状态与物流终态冲突；
- 需要执行退款、取消、费用调整或其他业务写操作。
