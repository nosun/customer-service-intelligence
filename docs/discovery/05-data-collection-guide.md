# 邮件模板与历史 Case 收集指南

## 目标

在不等待完整账号交接和测试环境的情况下，形成第一批可分析资料，用来确定 Case 分类、知识边界、客服判断规则和 MVP 的 Gold Cases。

## 一、邮件模板收集

模板分成三类收集，避免把不同用途混在一起：

### 1. 系统自动发送

例如注册、支付、订单确认、状态通知、发货通知。记录：

- 模板名称和来源系统。
- 触发条件。
- 发件邮箱和收件对象。
- 使用的变量及其来源。
- 是否仍在线使用。
- 客户回复后由谁处理。

### 2. 客服根据规则手动发送

例如进度说明、退款说明、退货步骤、补偿方案。记录：

- 适用的客户问题。
- 发送前需要确认哪些事实。
- 哪些条件下不能使用。
- 可以修改的内容。
- 是否需要审批。

### 3. 个人经验文本

包括 Gmail 草稿、复制粘贴话术和客服个人保存的片段。这些内容只能先作为 Raw Knowledge，不能直接视为公司 Policy 或 Approved SOP。

每个模板使用[邮件模板登记模板](templates/email-template-record.md)单独记录。

## 二、历史 Gmail Thread 收集

优先保留完整往返过程，不要只保留客户第一封邮件或客服最后一封回复。每个样本至少应看到：

- 客户最初问题。
- 客服追问和客户补充。
- 客服查询了什么信息。
- 实际回复和处理动作。
- 客户后续反应。
- 最终是否解决，以及是否退款、投诉、拒付或再次来信。

每个样本使用[历史 Case 登记模板](templates/case-sample-record.md)记录。

## 三、建议的第一批样本

第一批不用追求数量，先选择 20 个高信息量 Thread：

| 类型 | 数量建议 | 选择标准 |
| --- | ---: | --- |
| 售前 | 6 | 商品、尺码、颜色、定制或交期咨询 |
| 售后 | 8 | 质量、尺寸、退货、退款或投诉 |
| 生产/物流 | 3 | 进度、加急、物流异常 |
| 复杂或失败 | 3 | 多次往返、客户不接受、升级或拒付风险 |

同一类型尽量同时包含：处理得好的案例、需要多次沟通的案例、结果不理想的案例。

## 四、推荐的 Gmail 侧整理方式

如果当前客服仍可操作邮箱，可以先给代表性 Thread 添加标签，不必马上导出全部邮箱：

```text
CSI-SAMPLE/PRESALES
CSI-SAMPLE/AFTERSALES
CSI-SAMPLE/PRODUCTION-LOGISTICS
CSI-SAMPLE/COMPLEX
```

邮箱交接完成后，可通过 Gmail API 按标签做第一批只读同步。标签只是样本集合，不等于最终 Case 分类。

## 五、数据安全要求

- 不把原始 `.eml`、MBOX、附件或包含客户信息的文件提交到 Git。
- 调研记录中用 `customer_001@example.invalid`、`ORDER_001` 等替代真实身份。
- 去除姓名、电话、地址、支付信息、物流地址和附件中的个人信息。
- 脱敏映射如确实需要，应与分析资料分开保存并限制访问。
- 未经确认，不把原始客户邮件批量发送给第三方 AI 服务。
- 附件在后续正式接入时需要独立的访问控制、文件类型校验和安全扫描。

## 六、知识边界

收集时必须区分：

| 层级 | 含义 | 能否直接指导回复 |
| --- | --- | --- |
| Raw Data | 原始邮件、模板、客服实际操作 | 否 |
| Extracted Knowledge | 从案例中归纳出的模式 | 否 |
| Reviewed Knowledge | 负责人确认基本正确 | 可用于人工参考 |
| Approved Policy/SOP | 正式批准的规则 | 可以 |

“过去这样处理过”不代表“以后都应该这样处理”。特别是退款、补偿、取消和承诺交期，需要单独确认规则和权限。

## 七、第一批资料完成标准

- 至少登记 10 个常用模板，并标明自动/手动、来源和适用条件。
- 至少整理 20 个完整 Thread，其中包含售前、售后和复杂案例。
- 每个 Case 都记录客户诉求、客服动作和 Outcome。
- 至少找出 5 条仍不明确或不同案例处理不一致的业务规则。
- 选出 10 个可作为后续 AI 评估基线的 Gold Cases。
