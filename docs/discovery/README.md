## 当前成功标准

调研阶段完成时，应当能够明确回答：

- 第一批接入哪些站点、邮箱和渠道。
- 一封消息如何关联客户、订单和 Case。
- 四个已有项目分别提供哪些事实和操作能力。
- 哪些动作仅查询、哪些需要人工审批、哪些暂不接入。
- MVP 的真实业务闭环、测试数据和验收负责人。

## 已确认的试点信息

- 第一批站点：`dressafford.com`。
- 第一批客服邮箱：`support@dressafford-service.com`。
- 第一阶段目标：先同步客户来信并分析，不自动发送或执行业务动作。
- 业务量：日均客户邮件不超过 20 封。
- 主要语言：英语。
- 业务范围意向：覆盖客服收到的售前和售后问题。
- LiveChat：当前尚无可用账号，暂不作为 MVP 前置条件。
- 测试环境：当前未准备；后续计划通过受控线上测试订单完成端到端验证。
- 取消、退款、改地址、加急和补偿：当前由客服人员判断；客服近期离职，因此流程交接和决策依据沉淀是当前最高优先级。

## 需要业务方提供的第一批信息

先提供下面 8 项即可，不需要一次整理完所有历史资料：

1. 当前客服人数，以及即将离职客服的最后工作日期。
2. 售前和售后中最常见的具体问题及大致占比。
3. 确定即将离职客服的交接访谈时间和流程确认人。
4. 20～50 个有代表性的历史邮件 Thread，覆盖正常、复杂和处理失败案例。第一轮可以脱敏。
5. 客服对退款、取消、改地址、加急、补偿的实际判断方式和典型案例。
6. Gmail 账号完成交接后的只读接入条件。
7. 后续受控线上测试订单的范围、预算和负责人。
8. MVP 最终业务验收负责人。

不要在聊天或文档中粘贴密码、OAuth Token、API Key。需要接入时，再通过本地环境变量或凭据管理服务配置。

## 建议的协作节奏

1. 业务方回答第一批 8 项信息。
2. 根据样本邮件共同完成 Case 分类 v0。
3. 逐项确认四个系统的数据来源和写操作边界。
4. 冻结 MVP 范围和验收样本。
5. 再创建项目骨架、数据库迁移和接口适配器。

## 当前可以立即推进的工作

在邮箱账号、LiveChat 和测试环境尚未交接完成时，先做两类只读资料采集：

1. 收集自动发送和客服手动发送的常用邮件模板，并记录其适用条件和变量。
2. 选择包含完整往返回复的真实 Gmail Thread，整理客户诉求、客服判断、处理动作和最终结果。

原始客户邮件包含个人信息，不应直接提交到代码仓库。优先在 Gmail 中给样本 Thread 添加专用标签，或保存在受控的私有目录；调研文档只保存脱敏后的结构化记录。
