# 客服业务分类与流程

## 目标

形成一套客服、产品和研发都能使用的 Case 分类及处理流程。邮件、聊天和站内消息只是沟通渠道，Case 才是需要解决的业务问题。

## 当前业务背景

- 试点站点为 `dressafford.com`，客服邮箱为 `support@dressafford-service.com`。
- 日均客户邮件不超过 20 封，主要语言为英语。
- MVP 业务意向是覆盖售前和售后问题。
- 取消、退款、改地址、加急和补偿目前都由客服人员判断。
- 现有客服近期将离职，因此不能只交接“操作步骤”，还需要记录判断依据、例外情况和处理结果。

## 离职交接采集重点

建议用真实 Case 访谈，不要求客服先编写完整制度。每类至少选择 3～5 个案例：一个常规成功案例、一个复杂案例、一个处理失败或客户不接受的案例。

访谈时逐项记录：

1. 客户最初提出什么问题。
2. 客服如何确认客户与订单。
3. 依次打开哪些系统、查看哪些字段。
4. 哪些条件会改变处理决定，例如订单阶段、婚期、金额、客户历史和物流状态。
5. 客服可以自行决定到什么范围，哪些情况会询问其他人。
6. 实际采取了什么动作，为什么没有选择其他方案。
7. 最终客户是否接受，是否退款、投诉、拒付或再次来信。
8. 如果新人处理，最容易犯什么错误。

优先完成以下五类决策卡：取消、退款、改地址、加急、补偿。每张决策卡都要区分“常规规则”“例外情况”“需要升级”。

## Case 一级分类 v0

| 阶段 | 初始二级分类 | 需要关联的数据 |
| --- | --- | --- |
| 售前 | 商品咨询、尺码、颜色、定制、交期、优惠 | 站点、商品、库存/制作周期、客户 |
| 生产中 | 进度、取消、改尺码、改颜色、改地址、加急 | 订单、Order Item、Work Order、婚期 |
| 物流中 | 未发货、轨迹停滞、清关、丢件、签收争议、地址异常 | Shipment、Tracking Event、承运商 |
| 售后 | 质量、尺寸、色差、退货、部分退款、全额退款、投诉、拒付 | 订单、商品、支付、退款、历史 Case |

这只是起始分类。是否拆分或合并，以真实邮件样本为依据。

## MVP 覆盖口径

“覆盖售前和售后”在 MVP 中拆成两个层次：

1. 全量识别：所有来信都应识别为售前、生产中、物流中、售后或无法判断，不能丢失未支持的问题。
2. 深度处理：只对样本充分、规则已确认的问题提供订单/商品证据、SOP 建议和英文回复草稿。

其他问题进入人工队列，并记录客服最终处理方式，作为下一轮扩展依据。日均邮件低于 20 封，第一阶段可以保持全量人工复核，不需要以自动发送换取吞吐量。

当前先通过常用邮件模板和完整 Gmail Thread 建立分类。模板用于识别已有话术和触发条件，Thread 用于还原真实判断过程和 Outcome；两者都不能未经审核直接成为正式 SOP。

## Case 生命周期 v0

```text
new
  -> triaged
  -> waiting_internal / waiting_customer
  -> action_required
  -> resolved
  -> closed
```

同时记录：

- 优先级：low / normal / high / urgent。
- 风险：low / medium / high。
- 负责人及协作者。
- SLA 截止时间。
- Resolution：采用了什么处理方法。
- Outcome：客户是否接受、退款金额、是否重开、是否投诉或拒付。

## 每类 Case 需要整理的信息

业务方可按下面模板描述，不要求写技术术语：

```text
问题名称：
客户通常怎么描述：
客服现在如何判断：
需要查看哪些系统和字段：
可以采取哪些处理方式：
哪些情况必须升级或审批：
处理完成的判断标准：
最容易出错的地方：
```

## 样本邮件标注字段

每个历史 Thread 至少标注：

- 所属站点、语言、收件邮箱。
- 一级/二级 Case 类型。
- 客户、订单号、Order Item、婚期。
- 客户诉求与客服实际处理动作。
- 是否解决、最终结果。
- 哪一封客服回复较好或较差，以及原因。
- 是否适合未来自动化。

## 待业务确认

- [x] 第一批以英语邮件为主。
- [ ] 一个 Thread 中出现两个问题时，是否允许拆成两个 Case。
- [ ] 婚期临近多少天进入高风险。
- [ ] “已解决”和“已关闭”的业务区别。
- [ ] 退款、取消、改地址和补偿分别由谁审批。

- [ ] 客服遇到特殊情况时实际向谁升级。
- [ ] 离职客服最后可参与流程确认的日期。
