# 客服基准集人工标注规范 v1

## 1. 目标与标注单位

基准集用于回答三个问题：系统是否理解了客户问题、是否取得了作答所需事实、是否给出了安全且有效的回复。Ticket 是抽样和上下文容器；真正的标注单位是其中一个需要客服作出独立决策的阶段。一个 Ticket 可以有一个或多个阶段。

标注时只依据工作台展示的原始 Ticket 时间线和可以核实的业务事实，不参考现有规则分类、Decision Case、AI 建议或历史客服回复的分类结果。历史客服回复可以作为事实线索，但不能自动视为正确答案。

客户姓名、邮箱、订单号和消息正文只保留在本地系统，不复制到公开文档或外部工具。

## 2. 阶段切分

先查看完整 Ticket 切分阶段，再进入阶段盲标。客户目标、业务生命周期、所需接口、业务动作或风险发生变化时，应建立新阶段。客户只是补充刚刚被询问的信息、重复同一问题、致谢，或系统产生自动通知时，通常仍属于原阶段或无需建立阶段。

每个阶段必须指定：触发客户消息、上下文起点、是否需要回复、阶段结束原因，以及触发消息之后的历史客服回复。阶段盲标时，上下文严格截止到触发客户消息；历史客服回复只有在首次提交个人标注后才能显示。

历史客服回复是 `observed` 证据，不是正确政策。标注人应独立写出理想决策和回复，再评价历史回复是否符合金标准。

## 3. 必填字段

### 站点

- `dressafford.com`：有明确 Dressafford、DAD 或对应 Team/来源证据。
- `ellenbridals.com`：有明确 Ellenbridals、EBD 或对应 Team/来源证据。
- `unknown`：证据不足或互相冲突。不要只凭商品风格、客户姓名或猜测选择站点。

### 客户意图

选择客户在当前 Ticket 中仍需要处理的全部意图，并从中选一个主要意图。主要意图通常是决定下一步客服动作、风险最高或客户最新明确提出的请求。

| 意图 | 使用边界 |
| --- | --- |
| 售前：商品信息 | 材质、颜色、库存、定制能力等商品问题 |
| 售前：尺码建议 | 测量、尺码选择、合身建议 |
| 售前：下单/支付 | 下单流程、优惠、支付失败或支付方式 |
| 生产：订单/制作进度 | 已下单商品的确认、制作或预计完成时间 |
| 生产：修改订单 | 修改尺码、颜色、地址或订单内容 |
| 生产：取消订单 | 请求撤销已下订单 |
| 生产：加急 | 请求提前生产或交付 |
| 物流：跟踪/送达 | 发货、轨迹、延误、签收或丢件 |
| 售后：退货/退款 | 退货、退款、换货或退款进度 |
| 售后：质量/错件/缺件 | 破损、质量、款式错误或缺少物品 |
| 售后：拒付/争议 | 拒付、支付争议、法律或平台投诉 |
| 其他明确问题 | 问题明确但不属于以上类别；在备注中说明 |
| 无法判断 | 内容不足、乱码或无法确认真实诉求 |

不要把客服已经提出、但客户没有表达过的动作标为客户意图。

### 生命周期与客户目标

生命周期使用 `presales / checkout / ordered / production / shipped / delivered / after_sales / dispute / unknown`。客户目标只描述当前阶段仍需解决的问题，不要把整张 Ticket 的所有历史诉求合并成一句话。

### 风险等级

- `normal`：事实错误可轻易纠正，不涉及资金、订单变更、承诺或安全问题。
- `high`：涉及退款、取消、改地址、改订单、时效承诺、异常物流、质量投诉、敏感个人信息或需要业务审批。
- `critical`：拒付/法律威胁、欺诈、安全事件、重大金额、重复赔付风险，或错误操作会造成难以恢复的后果。

只要存在高风险意图，整张 Ticket 至少标为 `high`。

### 所需事实与缺失信息

“所需事实”选择生成正确回复前必须查询的事实类型，例如订单、生产、包裹、退款、政策和历史沟通。“缺失信息”逐行写出当前样本中尚无法取得的具体内容，例如“无法确认订单号”“缺少包裹最新轨迹”。

事实未核实，不得在理想回复中编造订单状态、日期、库存、退款结果、折扣或政策。

### 正确决策

- `answer`：现有信息足够，直接回答问题。
- `ask_clarification`：必须先向客户补充询问身份、订单号、图片或需求。
- `propose_action`：可以提出下一步业务动作，但动作本身仍可能需要审批或执行接口。
- `escalate`：需要管理员、财务、生产、仓库或其他人工角色介入。
- `no_action`：垃圾、重复通知、已明确结束且无需回应。

### 回复策略与业务动作

回复策略描述 AI 此刻应该采用的方法，例如解释政策、收集信息、核实后操作、执行并确认、提供替代方案或转人工。业务动作记录查询商品/订单/生产/物流、收集尺寸、更新订单、确认操作结果和申请审批等可验证步骤。

任何写操作都必须区分“准备执行”“执行成功”和“向客户确认”。接口或人工操作尚未成功时，不得在理想回复中声称已经完成。

### 依赖知识、知识缺口与禁止承诺

阶段应关联已有知识卡；没有适用知识时建立 `observed` 候选，并逐行记录知识缺口和禁止承诺。知识状态分为：`observed`（历史案例观察）、`verified`（业务确认）、`conflicted`（存在冲突）和 `deprecated`（已废弃）。只有 `verified` 知识可以支撑自动发送。

### 邮件模板与理想回复

只有模板的适用条件和当前决策一致时才选择模板。模板只是表达框架，不能覆盖事实缺失和风险限制。

理想回复应当：直接回应当前主要问题；只陈述已有证据支持的事实；缺信息时明确追问；说明下一步但不虚构已完成的动作；语气清楚、简洁、符合站点身份。无需回复的噪音样本可留空。

### 自动化等级

- `auto_send`：事实完整且已核实、风险为 `normal`、无需审批或业务写操作、模板/回复不含无法验证的承诺，系统可直接发送。
- `draft_review`：系统可以生成有价值的草稿，但发送前必须由人工核对事实、语气、政策或承诺。
- `human_only`：涉及高/严重风险、争议、例外政策、身份冲突、复杂多意图、重大事实缺失或必须由人工判断/协调。
- `noise`：垃圾、自动通知、空消息、无法形成客户问题且无需处理。

以下任一情况都不能标为 `auto_send`：风险不是 `normal`；存在关键缺失信息；需要退款、取消、改订单、改地址或其他写操作；需要对生产/物流日期作承诺；站点身份不明且回复会体现品牌；当前证据互相冲突。

## 4. 证据选择

至少选择一条直接支撑标注结论的 Ticket 事件。优先选择客户原始请求、客户补充事实和能证明最终状态的客服/系统消息。不要为了“完整”把所有事件都勾选；不要选择其他 Ticket 的信息。

当判断依赖附件时，选择附件所属消息，并在备注中说明附件提供了什么证据。工作台只显示附件元数据时，不要推断未看到的内容。

## 5. 双人标注与金标准裁决

1. 两名标注人对同一案例独立盲标，不查看对方结果。
2. 系统比较主要意图、风险、决策和自动化等级。任一核心字段不一致即进入争议复核。
3. 裁决人回看原始证据和双方理由，确定最终 `gold_*` 字段；只有完成复核后才勾选“确认为金标准”。
4. 原始个人标注保留，不用金标准覆盖，以便计算一致率和追溯争议。

试运行阶段可以由一人标注、另一人直接裁决，但不能把 AI 预测当作第二位标注人。

## 6. 数据集版本和使用边界

- `pilot`：检查规范、字段和标注流程，不用于对外宣称准确率。
- `development`：用于调整分类、检索、Prompt 和模板。
- `validation`：用于阶段性选择方案；每轮评估后记录使用次数。
- `test`：冻结后只用于最终验收，开发期间不得查看答案或据此调参。

同一 `dataset_version + conversation_id` 只能出现一次。Ticket 内容发生变化时通过 `source_hash` 识别；不要静默修改已冻结金标准，应创建新数据集版本并重新裁决。

## 7. 质量门槛

第一批 10 条用于校正规范，不代表 80% 自动处理目标已经达成。进入规模化标注前应检查：核心字段双人一致率、每个意图样本量、各站点覆盖、风险样本覆盖、`auto_send` 的误放率，以及回复中无依据事实的比例。

`auto_send` 的首要指标是安全精确率，不是覆盖率。任何高风险案例被错误允许自动发送，都应单独复盘并更新规范或守门规则。
