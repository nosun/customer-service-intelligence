# 产品问答 Draft：服务策略、内容质量与排版

更新日期：2026-10-19。本文描述当前本地实现和本次讨论确认的产品原则，不代表生产部署或正式发布验收已完成。

## 产品定位

产品问答同时承担解答当前客户疑问和沉淀商品公开参考信息的职责。

- 与商品本身密切相关、对其他购买者有参考价值的问题，优先在本轮完整回答，并建议公开展示。
- 依赖客户个人要求、需要多轮沟通的售前咨询，通常建议隐藏，并引导客户通过已核实的客服邮箱继续咨询。
- 缺少关键业务证据或没有可用承接渠道时，保留待人工核实，不编造商品能力、联系方式或后续承诺。

公开参考价值、本轮能否完结、后续承接方式是不同判断。缺少个人测量数据不必然需要转邮件：能够提供有依据的尺码表使用指导时，应先在本轮解答。也不能因为某条回复需要隐藏，就把它当作安全失败；隐藏展示的咨询草稿仍可以是 `generated`。

## 当前处理链路

```text
问题分类与独立请求识别
  → 查询当前商品、实时事实及已验证政策
  → 回答规划：服务策略、客户顾虑、证据选择和答复结构
  → 根据选定内容生成回复
  → 翻译
  → 独立质量审核
  → 必要时修订一次，再作最终审核
  → Laravel 业务保护与 HTML 排版
  → 保存 generated / blocked 草稿
  → 人工检查、编辑 → Preview → 人工 Confirm
```

服务策略并入现有规划阶段，不增加独立模型调用。Laravel 负责业务写入与最终保护；n8n 负责组织工作流。邀请客户发邮件不等于系统发送邮件，也不代表创建了后续跟进任务。

## 规划职责与契约

规划使用原问题、当前事实与已验证政策规则，不把政策回复模板或完整操作清单当作必答内容。生成阶段只接收选定的回答范围；审核独立读取完整证据，不能假设规划一定正确。

`customer-decision-v1` 记录客户目标、顾虑、回复结构，以及：

| 字段 | 含义 |
|---|---|
| `answer_units` | 每个独立请求、覆盖意图、事实键、政策 ID、选定回答要点和关键业务信息缺口 |
| `customer_inputs_needed` | 个性化推荐所需的客户信息，不等同于缺失业务证据 |
| `conditional_advice` | 尚未选用的替代方案；不能自动写成推荐 |
| `deferred_details` | 本次无需展开、可放到政策链接或后续环节的细节 |
| `incidental_unknowns` | 不影响所选安全答案的未知信息，不应制造额外的不确定表述 |
| `service_strategy` | 展示价值、本轮完结判断与后续承接方式 |

`service_strategy` 的当前字段：

| 字段 | 值或用途 |
|---|---|
| `public_value` | `general_product` / `individual_case` |
| `recommended_visible` | 是否建议公开展示 |
| `can_resolve_in_one_reply` | 当前事实和答复能否在本轮完成核心解答 |
| `response_mode` | `answer` / `email_handoff` / `human_review` |
| `reason` | 判断依据 |
| `contact_email` | 必要邮件承接使用的站点已配置邮箱，否则为 null |
| `email_context` | 后续邮件中需要提供的最少必要信息 |

当前契约要求个体咨询和非直接回答模式不建议公开。后台草稿区显示回复方向和判断依据；完整规划和审核结论保存在 `usage.decision_review`。

邮件承接必须使用站点已配置邮箱，提供清楚的后续动作，不留下仅靠问答页继续往返的追问。没有核实的邮箱时进入 `human_review`。不能因为进入邮件咨询，就承诺款式可改、费用、交期或客服一定会跟进。

## 内容与语言原则

优先级是：事实和政策准确 → 回应客户真正顾虑并保留重要限制 → 自然、体贴、容易执行 → 在此前提下简洁。

- 结合不同意图背后的共同购买决策，不按标签逐段拼接政策。例如，尺码与退货共同涉及选错尺码的风险。
- 客户描述是需要回应的顾虑，不自动成为已核实业务事实。
- 有事实不等于要写进回复。一般退货咨询不自动展开所有类别例外、承运商、表格和批准后的操作步骤；客户明确询问时则必须回答。
- 推荐替代选项时，同时说明影响购买决定的限制；没有推荐或选择该选项时，不自动附加它的例外条款。
- 使用明确、可执行、有证据的指导，不能为了显得有帮助而创造通用选码规则或保证合身。
- 内部约束通过自然动作实现。例如建议自行对照尺码表，不在公开问答中索取身体数据，也不把内部隐私规则生硬写进正文。
- 友好来自说明和建议本身，不依赖固定问候、道歉或额外承诺。简短问题可以只用一句自然的回答。

用于检验原则的案例，不是固定回复模板：

| 场景 | 正确方向 | 应避免 |
|---|---|---|
| 仅提供 As Shown，客户问其他颜色 | 直接说明现有颜色选择 | 从缺少图片元数据推断照片不存在，或额外说无法确认照片 |
| 身高、体重、常穿尺码＋退货咨询 | 回应尺码差异顾虑，给出测量对照方法和主要适用退货条件 | 推测具体尺码、机械堆政策、无关定制推荐 |
| “Is this dress able to altered?” | 保留 alteration 的歧义，隐藏的邮件咨询中收集修改内容及下单前/交付后的区别 | 将其等同于定制尺码，或承诺支持款式修改 |
| 已有明确商品事实 | 本轮完成回答并判断公开价值 | 无必要地转接邮件 |

## 审核与后端保护

审核检查七个维度：`factual_accuracy`、`relevance`、`actionable_guidance`、`natural_tone`、`decision_risks`、`intent_coverage`、`language_equivalence`。每项有理由和正文片段，全部通过才能批准。语气或相关性问题需要修订，不应伪装成事实安全问题。

审核同时独立核对服务方向：是否无必要转接、是否把个体咨询当作公开商品结论、是否留下无法承接的追问、邮箱和需要提供的信息是否有依据。修订最多一次；最终仍不合格时保留草稿待人工检查。

Laravel 再检查邮箱与站点配置、关键证据、隐私、独立意图覆盖及不支持的后续动作。规划的展示建议不能放宽已有隐私保护。`human_review` 或无效邮件承接进入 `blocked`。

当前实现的重要范围：只有使用核实邮箱、通过审核的宽泛修改咨询，可以解除 `request_other_customization` 的意图级拦截。具体但未经证实的款式修改、独立照片请求及订单信息等仍保留原保护。不能把这一改动理解成所有定制问题均可自动生成可用回复。

新决策流程不再用旧固定答案覆盖审核后的正文。内容保护完成后，仅作确定性的格式转换和安全处理。

## HTML 排版与本地核对

排版属于内容审核之后的程序职责，不依赖模型每次输出合规 HTML：

- Markdown 链接、HTTP(S) 裸网址转为 HTML `<a>`；邮箱可使用 `mailto:` 链接。
- 段落空行转为 `<br><br>`，段内换行转为 `<br>`。
- 处理已有链接时避免重复或嵌套，删除空链接；特殊字符正确转义。
- 清理不安全属性和协议；不安全标记会转义或删除。

`ProductQuestionReplyFormatter` 用于草稿保存及相关本地展示。确认差异中的回答按清理后的 HTML 展示，其他字段保持文本。编辑区保留 HTML 源码，下方提供隔离的实时效果预览；目前不是可视化富文本编辑器。

实时预览用于核对排版，远端 Preview 仍负责核对实际业务变更。展示清理不会修改已保存的确认令牌或既有 Preview 载荷；需要修改提交内容时，应编辑后重新 Preview。

## 模型、超时与排查入口

本地可使用 OmniRoute 的 Chat Completions 接口；配置项见 [n8n README](../../n8n/README.md#draft-模型提供方)。密钥只放 Laravel 环境配置，不写入文档、工作流或日志。记录的是配置的代理模型名称，不是对上游模型身份的独立证明。

提供方和模型参与输入指纹并记录到草稿，不静默回退提供方。结构化补全的单次总预算限制为 30–180 秒；格式异常最多重试一次且共享预算，传输异常不作自动 HTTP 重试。PHP 该端点的执行预算为提供方预算加 20 秒；Q&A AI HTTP 节点等待 240 秒。生产 PHP-FPM、代理等请求上限须与此匹配。

排查时依次检查：原问题与分类 → 当前事实和政策 → `service_strategy` 与选定要点 → 初稿 → 首次审核及一次修订 → 最终审核 → Laravel 拦截与格式处理。首次审核批评保留在 n8n Execution；草稿的 `usage.decision_review` 主要反映最终规划和审核结论。
