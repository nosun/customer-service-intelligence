工程细化见[首轮流程开发设计](../superpowers/specs/2026-11-13-seawave-multi-dress-first-round-design.md)、[分步开发计划](../superpowers/plans/2026-11-13-seawave-multi-dress-first-round.md)及[ebd20261105-1295离线模拟](../research/2026-11-13-ebd1295-first-round-replay.md)。设计模拟不等于真实邮件／Console／n8n全链路已接通。

业务依据为用户确认的[多件处理策略](../../2026-11-12-multi-dress-processing-recommendation.md)。用户提供的文件目前在仓库根目录，未在 `docs/` 下；本计划引用实际文件，不移动或改写原分析。其 11 月 13 日修订优先于早期统计描述；不以退款结果推断购买意图，不重新制定 Console 拦截规则。

**用户同日补充的最新规则优先：** 首信告知订单在确认期间暂停，并要求 48 小时内回复。仅针对已核实的两件多件拦截，48 小时无回复时允许按正常流程进入生产；三件及以上无回复仍暂停。超时内部处理规则不写进客户邮件。本文此前“不设 48 小时、所有超时均交人工”的建议已被该确认替代；这是待实现的业务规则，不表示功能已经启用。

本文是[Seawave 一期计划](seawave-customer-contact-phase-one.md)当前唯一推进的业务子集。**ETA 冲突和 comment 处理暂停。** MyDorris 仅只读参考；实际业务限于 Seawave 的 DressAfford / EllenBridals。

## 1. 这一步的目标

针对 Console 已经标记的多件事项，确定是否还需要联系；需要时生成一封准确、中性的意图确认邮件，经过复核后通过 Gmail CLI 发送，核验并记录首轮结果，交给人工接续。

首轮询问两个核心问题：**这些礼服分别用于什么人或什么用途，以及计划保留哪些、多少件。** 同款、同码、相邻码和不同款只是决定提问重点的线索，不能直接归类为买多留一。

同日结合[用户提供的 Dorris 实际邮件](../research/2026-11-13-multi-dress-email-template-reference.md)，首信结构完善为“当前暂停与 48 小时回复要求 + 适用政策简短说明 + 已核实商品清单 + 必要用途问题 + 明确保留选择”。两封样本主要差在是否列出商品，不能据此断定使用不同业务策略；不把保留一件取消其余预设为所有客户的选择。暂停与 48 小时要求已由用户单独明确确认。

若已有与当前商品一致的有效用途及保留计划，整理证据并建议交跟单审核，无需再发首信。AI 的“全部需要”结论不是跟单放行，不代表客户以后不会正常退货。

本阶段不自动接续客户回复、不催信、不推荐具体尺码、不采集全套测量数据、不处理减件或退款。客户新回复由现有同事在 HelpDesk 接续；只读发现回复用于停止无回复计时路径，不等于启用自动答复。唯一新增的自动推进设计是本文件规定的“两件、48 小时无回复”路径；客户回复后的放行、三件及以上的放行、制作要求发布等继续由现有人工流程处理。本文描述待实现的受控流程，本次只制定规格，不发送真实客户邮件或解除实际阻断。

## 2. Console 已负责的规则

本地 `CustomerContactAutoRules::multiDressMatches` 与策略文件核对一致：

- 只统计 dress，排除伴娘裙和花童裙。
- 排除后达到三件直接进入确认，不附加同类、尺码、定制等要求。
- 恰好两件时要求同一可识别类别、明确标码、相同且有序的尺码标签列表，同码或相邻码命中；不要求同款。
- 继续沿用首次付款、启用时间及未分单边界，不由 CSI 回扫全部多件订单、补建联系单或自行扩大拦截。

**CSI 以真实 `source=multi_dress` 事项作为业务入口。** 商品当前组合用于分析提问，不建立第二套拦截器。API `item_ids` 可包含整单配件，不能直接当作礼服清单。

当前公开 API 支持站点、订单、状态、分页和排序，没有声明 `source`、未发送或 released 过滤参数。先完整读取分页，在 CSI 本地筛选多件；不能凭空传参数并假定服务端已经过滤。后台筛选或本地规则调整也不等于新增了 API 契约。

## 3. 哪些进入首轮信息分析

候选需要同时具备：Seawave、站点匹配、source 为 multi_dress、未删除、尚未解除、事项未完成；订单仍已付款、未取消、未发货且没有开工证据。状态为 customer 仅是 Console 自动建档的初始状态，**不证明已经发信**。

每单先读取当前有效商品、全部关联事项、必要的完整历史及已有同目的沟通。分为：

| 结果 | 条件 | 本阶段下一步 |
| --- | --- | --- |
| 无需再联系 | 有明确用途及保留计划，且证据对应当前商品 | 中文整理及跟单审核建议；不发信、不解除 |
| 需要首信 | 意图信息缺失，事实足够，已有沟通与人工接管已排除 | 选择场景提问，生成实际邮件并独立复核 |
| 已有沟通在途 | 客服已联系、已有相关草稿/已发送、客户回复未处理或人工接管 | 停止首信；交当前负责人 |
| 当前事实过期 | 已取消部分商品、只剩一件、改款/改码或旧联系单与现状不一致 | 重新整理给人工；不按旧清单发信，也不自行解除 |
| 需人工判断 | 生产阶段不明、身份/事实缺失、政策争议、临近用期、风险或混合诉求会影响首信 | 保存原因及待核实点 |

**暂停 ETA/comment 的含义：** 不为其生成邮件、不翻译写回制作备注、不更新其事项。仍可只读识别是否有未决事项或客户指令，以免发出错误多件首信。存在独立、与多件询问无冲突的其它阻断时，多件问题可以单独准备；若这些事项改变客户是否继续购买、收件时点、沟通归属或邮件正确性，则交人工整合，不在本阶段拼接 ETA/comment 模板。发送后保留所有其它阻断。

## 4. AI 输出与首信分支

最小结构：当前有效礼服清单、商品组合事实、直接证据、已知用途/穿着者、已知保留数量、未知项、提问模块、适用站点政策引用及版本、是否需要发信及人工原因。每个商品的用途和保留数量均可为未知；事实、客户已确认、AI 推测分别保存。

| 组合线索 | 未确认时的提问重点 | 禁止推断 |
| --- | --- | --- |
| 同款、相邻码 | 同一人比较尺码，还是不同人需要；计划保留几件 | 已经在试码、必退一件 |
| 不同款、同码 | 不同场合/用途，还是希望收到后选款；是否计划保留全部 | 同一个人只会要一件 |
| 不同款、相邻码 | 穿着者或用途，以及是否比较款式/尺码 | 双重差异就是更高风险 |
| 同款、同码多件 | 数量是否有意、每件用途或穿着者、保留计划 | 重复添加或重复订单已成立 |
| 三件以上或其它组合 | 按商品/数量了解用途和保留计划，允许混合意图 | 全部用于挑选、全部定制可免确认 |

已知内容不重复问：客户已说“两场活动分别穿”，只需补保留计划；已明确两个人使用且全部需要，不再发通用信。只说“Yes / Both / All”但缺乏本轮问题上下文，不能自行补全用途。无需索要穿着者真实姓名，关系或用途足够。

若客户已明确只需要一件或部分商品，但尚未选定，使用“选择拟保留商品 + 提供选款/选码帮助”的模块，不再问是否全部需要；已经明确具体选择的，整理交人工处理实际变更，无需再发相同确认信。一期使用一份基础模板及有限提问模块，不按推测意图自动升级为强制减件或强硬拒退邮件。

公开 OrderItem 当前不提供类别及有序尺码表。不能由尺码数字差一推断相邻，也不能按款号猜类别；缺少可靠资料时使用通用询问，仍可处理已存在的多件事项。若要给具体选码建议，再接入真实商品尺码资料，属于后续独立工作。

## 5. 可审阅的首信文案

以下方括号为业务变量示意；不是已发布模板，也不是 Manager 已确认变量语法。正式正文使用客户可识别商品编号、款式、颜色、尺码和数量，隐藏内部工单/沟通单 ID。相同商品数量大于一时也明确数量。

首信采用通用主体，按订单填充商品及必要问题。两件与三件及以上均告知暂停、要求 48 小时内回复；件数影响内部超时处理，不需要在首信中披露不同后果。已有充分确认或人工沟通在途的订单仍不重复发通用信。

主题：`Please confirm the dresses in your order [order number]`

```text
Hi [first name],

Thank you for your order with [brand]. Your order is currently on hold
while we confirm your selection. Please reply to this email within 48 hours
to let us know which dresses you would like to keep.

Your order includes the following dresses:

[Item reference] — [style], [colour], size [size], quantity [quantity]
[Item reference] — [style], [colour], size [size], quantity [quantity]

Our return policy does not support ordering multiple dresses with the
intention of keeping only one and returning the rest. Any return request
remains subject to the conditions and exclusions in our return policy:
[Verified site return-policy link]

[One relevant question about the purpose or wearer, only if not already known.]

Please reply to let us know your plans:

- If you plan to keep all the dresses, please confirm this.
- If you would like to keep only some, please identify the items and quantities.
- If you are still deciding on a style or size, let us know what you are unsure
  about so our team can help you review the options before production.

Best regards,
[Brand] Customer Service
```

用途问题按事实选择，已经明确时省略：

- 通用/不同款同码：`Are these dresses for different people or occasions, or are you planning to compare styles or sizes after they arrive?`
- 同款相邻码（有可靠尺码表时）：`Are the two sizes for different people, or are you deciding which size would suit the same person?`
- 同款同码多件：`Could you confirm that the quantity is intentional, and let us know whether the dresses are for different people or uses?`
- 已知同一人有多个用途：只补未知的具体对应关系；不再询问是否不同穿着者。

基础模板用于尚未明确保留计划的订单；有明确部分保留意图时删去重复或不适用选项。客户可同时对不同商品有不同计划，不强制每单只能选择一项。政策段落为待审原型，正式使用前按站点核对当前条款并绑定已批准版本；已有客户特批或政策争议交人工。

商品清单只列经实际 type 和状态核实的相关有效礼服。样本中的 Size 空白可能是无尺码商品或缺失数据，不能按清单行数统计裙子；礼服关键属性缺失时先核对或转人工，不输出空的 `Size:`，也不自行补值。

文案包含已确认的“当前暂停、48 小时内回复”，不包含新的拒退条款、退款比例、保证赶上活动或工厂已确认等说法。不概括为“只要未穿无损即可退”，也不将买多留一限制扩大为所有正常试穿/合规售后均拒绝。来单生产原因如需加入，只使用有当前依据的批准段落；有现货/快发商品时不能一概声称全部按单制作。活动日期、尺寸测量和备注要求不塞进这封首信。

“当前暂停”是必需告知的事实，发送前核实订单仍处于相应阶段；若已经恢复、取消或开工，应停止过期首信，而非只删除暂停段落后继续发送。不把该句写成 AI 新执行了暂停。邮件不说明无回复后的内部生产规则，也不能声称“未收到回复就绝不开始生产”、自动取消或其它与内部规则不符的后果。

### 5.1 48 小时等待与内部处理

用户已确认的对客要求是 48 小时内回复，内部按两件与三件及以上分流。建议实施时从首封实际发送成功的时间起算连续 48 小时，保存首次发送时间及截止时间；草稿、发送失败或结果未知不开始计时，重试和重新分析不重置期限。这个计时起点是实施建议，接口联调时需与 Console 现有行为对齐。

| 计时期间/截止时事实 | 内部动作 | 是否自动接续客户邮件 |
| --- | --- | --- |
| 48 小时内有相关客户回复 | 退出无回复路径，交人工 HelpDesk 按回复处理 | 否 |
| 截止时仍无回复，已核实的两件多件拦截，且无其它未决阻断或人工暂停 | 按当前有效订单恢复正常生产流程；保留实际执行结果和超时依据 | 否；不额外发信说明内部超时规则 |
| 截止时仍无回复，三件及以上多件拦截 | 保持暂停，形成内部待跟进事项，由人工继续处理 | 否；不自动催信、取消或放行 |
| 有回复但答案不完整、未作选择或正在人工处理 | 继续等待人工处理，不再归类为“无回复” | 否 |
| 有其它未决阻断、人工暂停、商品变化、投递失败或消息读取不完整 | 停止自动推进，交人工核实 | 否 |

两件判定以 Console 多件规则的核实结果为准，保留原始触发组合与当前有效商品证据，配件和 Service 不算礼服。不能只按 contact.item_ids 数量或清单行数判两件；不能给原本三件及以上、后减为两件的订单直接套用两件超时规则。API 不能证明商品范围和件数时，先转人工或补齐事实，不扩大自动推进范围。

到期执行前重新检查 Gmail/HelpDesk 的相关入站消息和人工接管；未读完、无法唯一关联、疑似自动回复或到期后执行前已收到客户消息时，先交人工，不把“未作明确确认”当作“无回复”。此检查仅用于判定超时分支，不自动理解并回复客户。

两件超时只提供解决多件等待的依据，不能忽略 ETA、comment、风险或其它未决原因。按源系统现有可执行流程处理目标多件事项，禁止借用一次解除全单所有事项的审核入口绕过其它阻断。解除阻断、恢复分配、实际开工分别核实，不把发出请求写成生产已经开始。

超时记录应表述为“两件首信发送后 48 小时无回复，依已确认内部规则继续”，不能记录成“客户已确认全部保留”。没有客户回复不构成客户陈述。

首封及内部超时判断属于当前首轮流程设计；真实回复后的第二封、第三封应根据已确认的保留选择、选码疑问或其它问题分别处理。自动接续回复仍放在 HelpDesk 第二阶段，当前由同事处理。

## 6. 复核、发送与记录

生成和审核分开。程序核对站点/实际 Gmail 账号、订单客户收件人、商品/数量/尺码/颜色和内容摘要；AI 独立复核是否漏掉已知条件、重复询问、带入未经确认意图或额外承诺。复核不通过最多修订一次，再不通过交人工。

源分析文档规定 AI 不直接发消息：模型只输出建议与正文，不获得发送工具/凭据。发送必须由受控服务依据已发布策略和审核后的固定内容执行。保持之前“可由 AI 复核、不要求逐封人工审批”的架构；**本轮仍先做草稿与影子验证，未据文案草案启用自动发送**。

发送前重新读取关键订单/事项状态、最新相关消息及人工接管，绑定已复核的商品和邮件内容；变化则审核失效。客户端最后读取与外部 Gmail 发送无法跨系统原子化，发现竞争后交人工，不把本地锁当作 Console 人工编辑锁。

执行流程：

```text
Seawave 多件事项
→ 同单事实与沟通去重
→ 无需联系 / 需要首信 / 人工处理
→ 模板及必要问题
→ 程序校验 + 独立 AI 复核
→ 持久化审核内容和发送意图
→ Gmail CLI 单次发送
→ 按返回消息 ID 核对 SENT、实际收件人和内容
→ Console 追加内部备注，recorder=nosun-agent
→ 保存 48 小时等待期限
→ 收到回复：停止无回复路径，HelpDesk 人工接续
→ 两件且 48 小时无回复：核实其它条件后按正常流程推进
→ 三件及以上且 48 小时无回复：继续暂停，交人工跟进
```

首轮唯一键按 `seawave + sid + oid + first_round` 建立，不以重新分析时间、模板版本或 contact_id 产生新一轮。历史沟通建立接管基线，已知发送或 unknown 不再发；同单新增事项不自动触发第二封。发送成功但写回失败只补写备注。

Gmail CLI 发件箱回查已用测试邮箱验证；尚不代表 EllenBridals 单独发信、客户实际收件及回复转入 HelpDesk 均已验收。SENT 记为 Gmail 已发送，不写客户已收到。记录返回 Gmail ID、真实 Message-ID、线程 ID及本地动作标识；超时先对账，查不清不重发。

发信记录适配器只追加 `internal_note` 并设 `recorder=nosun-agent`，不因发送首信自动改 `status`、`customer_requirement` 或放行字段；实际 API actor 保留绑定账号。使用最新 version、Preview/Confirm、幂等键和回读，保留人工原文。两件超时推进作为独立、受限动作实现，不把写备注当作已经解除阻断；当前未启用此执行器。

若通过 trade MCP 执行业务写回，遵守用户最新 MCP 约定：展示实际预览并取得用户授权后才能 confirm，不能把 operation_id、AI 复核或本设计当作人工授权。本阶段没有执行该类写操作。

日志示例：`[nosun-agent][首轮ID] 多件首信已由 Gmail 发送并回查；待确认两件用途及保留计划。后续回复由人工 HelpDesk 接续。` 草稿/unknown 必须如实记录，不能套用“已发送”。

## 7. 按步骤推进与完成标准
