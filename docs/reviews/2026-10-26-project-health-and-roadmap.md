## 需要优先处理的问题

### 1. P1：SDK 任务未纳入现有健康与失联恢复范围

证据：`app/Services/TicketWork/TicketDraftWorkflowHealth.php:12` 和 `app/Console/Commands/ReapTicketDraftWorkItems.php:26` 都筛选 `TicketWorkItemManager::WORK_TYPE`，即 ticket_draft；SDK 使用 ticket_agent。UI 通过 background connection 启动 SDK，见 `app/Admin/Controllers/TicketAssistanceController.php:34`。

结果是 SDK 即使失败或卡住，现有定时健康检查也看不到。当前数据库正好能观察到：SDK 最近记录含失败，而 Ticket health 仍可返回 healthy=true。

SDK 有进程内异常处理和 Job.failed 回调，已有保护；但父进程/机器直接终止等场景不能完全依靠该回调。WorkItem 设置 deadline 不会自行终结状态，现有 reaper 又不处理 ticket_agent。当前未发现实际挂死任务，这是源码可确认的恢复覆盖缺口，尚未做进程强杀演练。

建议：统一统计两个 Ticket work_type，保留 workflow/version 维度；增加 SDK 过期任务收尾，先标失败并人工重跑即可，不必引入复杂续跑。验收包含进程中止、超时、重复派工及迟到结果不得覆盖新任务。

技术健康、产物可用性、人工采纳与业务完成应分开展示。自动派工关闭或观测窗口没有任务时显示 disabled/no_data，避免给出宽泛的“系统健康”。

### 2. P2：常规测试入口遗漏 Unit 和 Node

证据：`phpunit.xml:7` 只配置 tests/Feature；composer test 最终调用 php artisan test，根 package.json 也没有统一 test 入口。仓库未发现 .github CI 配置，未排除仓库外的检查。

62 项 Unit 覆盖 n8n 审核保护、回放门禁、格式化等关键行为，23 项 Node 覆盖 SDK 调用、修订与审核。一句“全量测试通过”如果只执行默认命令，会漏掉它们。

建议：统一一条检查命令，包含 Feature、Unit、Node、return-flow-check 及必要格式检查。真实模型回放独立运行，不加入每次常规测试。验收要求每一组故意失败时统一入口返回非零。

### 3. P2：SDK 输入指纹没有覆盖自身运行版本与模型选择

证据：`app/Services/Agents/TicketAgentTools.php:68` 借用 ticket-draft-v2@2.0.0 的输入，再加入 Return 定义和会话内容；未加入 SDK workflow version、Node prompt version、模型/provider。`TicketAgentWorkflow::create` 的活动任务复用查询也没有按 workflow_version/provider 区分。

本轮只在独立 PHP 进程中改变模型/provider 配置后重新计算指纹，结果相同，未修改持久配置。改变 Return 定义会失效，单独改变 SDK 实现版本或模型则没有同等保护。

影响：相同会话的旧版本或另一 provider 活动任务可能被复用；旧结果的“当前有效”判断也无法表达 SDK 版本升级。报告里记录了版本并不等于版本参与失效判断。

建议：在创建任务时冻结 SDK 运行规格，包括 workflow/prompt version、provider/model、策略哈希；将它加入去重与有效性判断。升级后旧结果保留历史，但不能继续标为当前版本结果。验收覆盖只改变 prompt/model/provider、其他输入不变的情况。

### 4. P2：智能体反馈后的重新分析固定回到 n8n v2

证据：`TicketAssistanceController.php:66` 的 regenerate 分支直接创建 ticket-draft-v2；`TicketAssistanceDispatcher` 的自动派工同样固定 v2。SDK 则有完整独立调查、拟稿和审核路径。

这是渐进实验阶段可以接受的并行，但当前交互没有保存“沿用原执行路径”的语义。客服纠正一个 SDK 结果后要求重跑，实际收到的可能来自另一套流程；Return SDK 的节点能力也不会因此自动带到 v2。

建议：反馈重跑默认沿用所针对任务的执行路径，显式切换时记录原因。自动派工先保留基线，通过同一冻结案例对照后再决定范围切换。暂不建设通用 Worker 插件体系。

### 5. P2：SDK 尚未接入统一发布门禁

证据：`TicketAgentWorkflow::create` 未经过 WorkflowRegistry；`WorkflowReleaseGateRegistry` 只注册产品问答与 Ticket v1/v2，没有 SDK key。

手动、待人工审核的实验入口可以保留，但不能因为 SDK 语境案例通过就直接把它扩展为全量自动派工。当前业务保护不等于统一的版本准入、回滚和人工案例验收。

建议：扩大使用前复用现有候选、验收、启用、回退的原则；登记 SDK 独立评估结果，至少先提供明确候选版本和可选择基线。无需先把所有 n8n 专有登记逻辑重构成通用引擎。

### 6. P2：文档入口已落后，缺少明确退役清单

README:3 仍定位为 Gmail 采集分析 MVP，README:33 称后台只读，与当前本地反馈、草稿及智能体入口不符。第一阶段方案仍主要描述 v2 映射与 SDK 替换调查节点，当前 SDK 实际已提供完整调查、拟稿、审核路径。

这些文档分别可以解释历史，但缺少一张当前路径表来确定默认入口、候选入口、维护状态和退役条件，会使后续开发继续向不同方案加功能。

建议：README 只负责当前产品定位、启动、统一检查和导航；一份当前路线图列清主链、实验、冻结和历史。旧文档保留日期与历史状态，减少重复维护。

## 测试的真正缺口

最值得补充的是已有保护边界之外的故障与版本测试：SDK hard-stop 后恢复、模型或 prompt 单独变更使旧结果失效、SDK 反馈重跑保持路径、统一健康检查统计 SDK、统一测试入口涵盖全部套件。

现有 PHP 工作流测试通过 mock TicketAgentWorker 验证业务落库，Node 用脚本模型验证真实 Runner。两层都有价值，但未见完整覆盖 PHP/Node NDJSON 双向管道异常的自动化集成检查。可增加一个不访问模型的进程契约冒烟，验证消息分段、错误退出和超时；不需要为每条邮件重复建立同样的管道测试。

重点避免为每次措辞调整复制一组测试、为同一个已退役入口永久维持专属行为用例，以及把一次成功的模型回放当成总体可靠率。

## 建议路线图

| 批次 | 交付 | 完成标准 |
| --- | --- | --- |
| A：修正运行与验证盲区 | SDK 健康/过期恢复、运行规格指纹、统一检查入口、当前路径文档 | 模拟失联能收尾；版本改变不复用；一个命令覆盖所有本地检查；两条路径可分别观测 |
| B：选择日常主路径 | v2 基线与 SDK 在同一小批固定 Ticket 上对照；反馈重跑保持路径；补齐候选版本准入 | 人工逐案评价分析/建议/草稿，记录遗漏、错误承诺、编辑分钟数、时延和成本；按场景决定启用范围及回退方式 |
| C：做一次可验证的减负 | 冻结并退役旧 PoC、核实后收缩 QA 旧回复分支、去掉退役入口专属测试、整理 README 与历史文档 | 入口与调用证据支持删除；保留的关键业务案例全部通过；没有增加新的重复执行链 |
| D：补最有业务收益的能力 | 按真实 blocked 原因增加费用/币种、退运查询、收货/质检等必要只读能力；形成一次反馈到知识发布闭环 | 每个接口对应实际阻塞案例并减少人工调查；知识修订经审核、有版本、可回滚且新案例能引用 |

B 的案例集建议先选择 20–30 个去重、覆盖当前业务分布的冻结案例，并涵盖已有客服回复后的新进展、附件不可读、身份不符、多商品、条件接受及接口故障。这是建议的首轮范围，不是已验证的发布阈值。基线与 SDK 应使用同一时间截面证据；实时调用另计，避免把事实更新时间不同当作执行框架优劣。

阶段目标继续保持“情况分析、处理意见、邮件草稿”，用人工减少的调查和改稿时间衡量收益。WeKnora 先完成一次审核→更新→索引→实际检索→新案件引用的闭环；当前不宜把扩大知识平台作为主线前置条件。自动发送、退款与订单写操作另行立项验收。
