# Codex 客服实践与现有框架：效率审查和最短实施路径

日期：2026-10-24。性质：本地只读审查和实施建议。未发送邮件、调用真实业务写接口或发布工作流。

用户已明确：同事实践中的“90%”指约 90% 的邮件无需逐封人工确认即可发送，作为远期参考。随后明确本系统第一阶段以稳定自动形成“情况分析、处理意见、邮件草稿”为目标。当前实施以 [第一阶段方案](../architecture/ticket-assistance-phase-one.md) 为准；本审查下文涉及发送的内容保留为后续能力研究，不作为本期前置条件。周报用于核对业务量、分工和统计范围；自动发送比例的独立验证仍需要逐项发送记录。

## 1. 判断

同事的实践说明，具备足够业务工具、清楚的操作流程和持续运行机制的 Agent，可以完成大量实际客服工作。现有框架不会因为组件更多而天然做得更好。它应通过减少人工处理时间、改善完成质量、支持稳定持续运行来证明价值。

当前首要差距是执行闭环和工具能力，并非缺少更多 Agent：现有 Ticket 主路径仍是人工触发调查、保存本地草稿；SDK 实验甚至只输出物流调查报告。把这个状态同一个已经连接邮件发送和业务 API 的运行体系比较，会把能力范围差异误认为模型或框架优劣。

建议沿用 Laravel 的状态和业务保护，收敛每个案件的智能处理入口，先打通批量领取、调查、生成、复核、受控发送和等待恢复。用真实邮件分布确定覆盖顺序，不先扩建通用多 Agent 平台。

相对上一轮完整目标规划，实施顺序应收敛为可每天运行的最小处理闭环；完整优先级模型、多 Agent 分工平台和自动知识分析不作为首轮发送闭环的前置条件。同步基础已存在，先核查运行并复用。

## 3. 当前代码审查

以下基于本次本地源码，未验证生产 Scheduler、队列、渠道授权或在线工作流状态。

### P0：自动处理入口与发送结果链路尚未闭合

- `routes/console.php:12` 已有 Ticket 每十分钟增量同步配置，`SyncHelpDeskIncremental` 有分页、游标、导入和锁；已有基础应复用。
- `ConversationController::generateDraft`（129 行起）由页面操作创建 WorkItem，177 行明确只保存本地、在 HelpDesk 发送。`TicketWorkItemManager` 的工作类型是 `ticket_draft`。
- `N8nTicketDraftService` 的成功结果仍是草稿或需人工审核，387、445、463 行明确保留 `requires_human_review=true`。模型复核通过不是发送授权。
- 已检查的 HelpDeskClient 只有列表读取；GwsClient 公开能力为 listThreadIds/getThread，没有发送与发送结果对账。不能把 Gmail 历史分析导入视为现有 Ticket 运行链路已经支持 Gmail 自动处理。

影响：同步和生成质量提升后，仍需逐封启动、查看、复制和发送，难以达到低人工介入目标。

建议：新增一个批量扫描/派工入口，复用 Case/WorkItem 和 lease；通过明确的渠道适配器发送，经唯一发送记录、远端回执与结果待核实分支闭合。实际邮件写权限必须在完成可审查实现后单独发布，审查任务不授权真实发送。

### P0：Agent 能力不足以替代日常客服操作

- `agents/ticket-investigator/src/investigator.mjs` 当前只有 read_facts 和 read_policy。事实来自冻结快照，不是动态外部查询，且提示限定物流调查、不生成客户回复。
- `TicketInvestigationInput::FACT_KEYS` 只有九项订单和物流标量；不提供生产细节、实际追踪号、退款凭证或附件内容。这符合首轮实验设计，不是生产覆盖能力。
- `TicketRuntimeContext` 传附件名称、类型和大小，没有把图片、视频和凭证内容交给调查。
- `TicketReplyPlan:131` 的补查范围只有 refresh_order；生产接口虽然有不少信息，Agent 不能据此自行查承运商、读取附件或完成外部协作。

影响：复杂售后需要人工补资料；“有 Agent SDK”无法补偿缺失工具。

建议：按案例覆盖价值增加少量业务工具，优先复用现有 Client：读取当前对话和关联历史、查询已核验订单、按需读取生产/包裹事实、读取适用政策、创建人工待办。附件读取及承运商补查按真实需求接入。模型不获得任意 URL、Shell 或业务数据库能力。

### P1：智能步骤分散，有重复理解与中间结果维护成本

- v2 JSON 有独立 Planner、Assessment、条件 Reassessment、Writer、Reviewer、Repair、Final Review；常规回复路径四次模型调用，有补查和修订时可到七次。
- 独立审核有价值；把每个内部推理阶段都拆成跨进程节点，则会增加调用延迟、协议维护和中间上下文传递。
- SDK 实验目前旁路运行。正式链路如果保留原 Planner/Assessment 后再插入完整 Agent，会重复调查。

建议：新候选路径由一个案件 Worker 负责“理解、受控调查、处理方案、候选回复”，完成后强制独立复核。Worker 可能有多轮工具调用，不能宣称固定两次模型请求；以整案调用数、时延和总成本实测。对简单场景探索一轮候选生成加一轮复核，对复杂场景有界补查，修订后必须重新审核。

把快路径作为可对照候选，不直接改掉现有 v2；同一任务只选择一条执行路径。验证通过后再替换重合职责，避免永久维护三套完整实现。

### P1：部分草稿保护不能原样当作自动发送策略

- `N8nTicketDraftService:260` 起统一检测姓名、订单号、邮箱和电话号码，可能阻止给已核验客户展示必要的订单或物流标识。
- `TicketPolicyRepository` 默认读取 draft 用途政策；KnowledgeResolver 已有 usage 参数。verified 或存在 automation_tier 字段，不等于可以自动发送或执行。
- `TicketResponseAssessment:55` 保存 follow_up_note，但明确不创建定时任务；进度描述尚未成为可唤醒的跟进工作。

建议：模型上下文按必要范围脱敏；对客户展示的姓名、订单标识、物流链接由 Laravel 从已核验对象受控填充。最终复核必须覆盖实际渲染后的内容和引用版本，防止填充后绕开审核。自动发送另行验证适用用途、站点、声明和权限。将跟进条件及到期时间落入可执行任务，不仅保存自由文本。

这些是能力与设计适配问题；本次没有量化误拦率，不能断言它们已经造成多少生产失败。

## 4. 最小目标结构

```text
同步 / 新消息 / 跟进到期
  → Laravel 派工、去重和领取
  → 案件 Worker（同一案件的唯一调查负责人）
      → 按需读取事实、政策与相关材料
      → 处理建议 + 候选回复 + 必要待办
  → 独立复核 + Laravel 动作授权
      → 白名单沟通：渠道发送、记录回执
      → 需人决定：完整交接并设置等待条件
  → 新消息或到期恢复
  → 处置反馈与实际结果进入定期复盘
```

Laravel 持有案件、动作与消息状态。队列可以并发处理不同案件；同一订单有冲突的写操作应串行。专业 Agent 只在工具域或上下文确有分界时增加，且不能独立发送同一案件的多封回复。

n8n 固定处理批量采集、报告、通知和已有确定子流程；新的单案件快路径可由 Laravel Queue 直接调用现有 Node Worker，不要求先增加 n8n 节点或常驻 HTTP 服务。调查工具需要受控内部调用时，再增加最小案件授权协议，不把所有业务凭据放入 Node 环境。

采用一个 Worker 加强制 Reviewer 是第一轮候选。Codex 与 Agents SDK 是不同运行载体；目前没有同事源码和同输入评测，不能判断哪个更强。复用同事实践时优先迁移 SOP、案例和工具契约，让模型执行载体保持可替换，不同时建设两个生产引擎。

## 5. 覆盖策略与权限策略分别推进

“回复有关退款的问题”和“执行退款”分开。现行政策明确时可以自动解释退货步骤、索取缺少材料或说明已核验的处理进度；退款资格特批、金额承诺和支付执行仍需对应授权。

| 业务簇 | 首轮处理目标 | 扩大自动发送前的依据 |
| --- | --- | --- |
| 普通进度与物流查询 | 最新事实、可核实链接和状态说明 | 身份和订单唯一、事实新鲜、不承诺无证据 ETA |
| 生产进度 | 有依据的当前制作阶段 | 不把估计交期解释为工厂保证 |
| 退换货流程与资料澄清 | 解释现行步骤、最少必要材料 | 不引入退款比例、资格特批或未完成动作 |
| 简单补充消息、致谢 | 合理确认或建议暂不回复 | 完整上下文、没有新诉求、有后续跟进责任 |
| 签收争议、损坏、财务例外 | 调查包、处理选项和邮件草稿 | 补齐凭证和相应人工决定 |
| 取消、改码、退款执行 | 调查与受控人工交接 | 独立业务授权和源系统结果核验 |

覆盖业务簇按实际分布排列，不假定这些类别天然占 90%。每个簇优先整理现有 KnowledgeArticle 的 action_steps、decision_tree、required_facts、templates、escalation_rules，补正可执行步骤和例外条件，不重新发明一套平行 policy 文件系统。

## 6. 最短实施次序与验收

### 第一步：对照真实工作，建立共同基准

先抽取连续一周需处理邮件形成进入队列的固定 cohort，并对稀有高风险问题补充独立测试集。全量自动化率以自然分布计权，不能用补充高风险样本改变业务占比。保留无需回复、已回复、等待中的真实分类，不先过滤出容易案例再计算总体覆盖。

若能取得同事资料，优先看三个高价值材料：主 worker 的任务和边界定义；邮件/订单工具脚本与权限；一批从领取到发送、人工交接、后续结果的匿名记录。无需先迁移全部 worker。

在相同输入时间和政策下比较当前 v2、单案件 Worker 候选、可获得时的同事方案；保留完整调查证据，避免后续结果泄漏给历史回放。人工评价准确性、遗漏、回复可用性、必要接管及耗时。历史正确答案也需复核，不能默认历史回复全都正确。

比较时尽可能统一模型与可用工具；无法统一则记录实际模型、推理配置、上下文、工具和价格，将运行载体与模型能力的影响分开，不归因于 Agent 数量。

验收：得出每个业务簇的占比、主要阻断原因和实际人工分钟数；明确 90% 指发送、辅助完成还是最终解决。

### 第二步：打通自动处理到人工接手

复用同步和 WorkItem，加批量派工、单案件 Worker、独立 Reviewer、自动保存草稿和结构化人工交接。第一轮正常业务尽量有处理结果，缺工具或无权限时有具体转交原因。先记录高风险原件的准备与脱敏，再按既有数据授权运行；不因本次审查直接上传客户邮件。

验收：可无人逐封点击地持续产出工作结果；重复扫描不重复处理；人工接管期间不抢发；关键资料缺失不编造；技术失败可恢复；同订单冲突受控。

### 第三步：接通一个渠道的可验证发送

选择当前实际服务渠道，先复用 HelpDesk 路径，避免同时引入 Gmail 的第二套生产状态；如果实际目标已经迁到 Gmail，再明确以 Gmail 为主。实现发送前最新消息检查、已回复检查、案件锁、发送唯一记录、远端消息 ID、超时核实、停用开关和审计。

不要把“重试三次”直接用于无幂等保障的邮件写操作。发送超时可能已成功，应先回查；远端无法可靠核实则转人工，不能盲目重发。

验收：受控测试邮箱完成完整发送与回读，故障测试覆盖超时、重复派工、人工并发回复、新消息和过期事实。正式开通需选定业务簇和适用权限，不以关闭 requires_human_review 字段代替实现。

### 第四步：按阻断原因扩大覆盖

每天汇总事实缺失、政策不明确、工具不可用、格式问题、正确接管、错误接管、模型错误和发送不确定等原因。优先修复占比高且可验证的前三类。按业务簇扩大自动发送并持续记录结果；将高频例外沉淀为新用例、工具或已审核 SOP。

真正需要专门上下文时再拆物流/生产/售后 Agent；确需跨天复杂恢复时再评估新编排系统。先证明复用现有 Queue/lease 无法经济处理，不提前引入 Temporal、多个向量库或复杂主从 Agent 群。

## 7. 衡量指标

- 自动回复率：固定进入队列 cohort 中，规定窗口内未经逐封人工确认、实际自动发送正确回复的邮件/回合占比。窗口尚未到期记录处理中，不冒充成功。
- 自动解决率：以案件为单位，观察期内无需人工、问题已解决且未重开；与邮件回合回复率分开。
- 人工介入率和人工分钟数：既包括升级处理，也包括隐形检查、改稿、重新运行和纠错。
- 质量：错误事实/政策、遗漏诉求、误承诺、错误不回复、重复发送、越权、重开和投诉。
- 效率：首次有效回复、最终解决耗时、整案模型请求数/token/工具成本/人工成本；不同运行载体使用同一口径。

另外单列“已授权业务簇内的自动率”和“全部需处理业务的覆盖率”，防止把扩大排除范围当作提高自动化。90% 是待检验目标，现有汇总表不足以推导本系统可达到的比例或开发周期。
